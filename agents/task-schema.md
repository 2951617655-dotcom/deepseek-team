# 结构化任务单格式规范

> 创建目的：为团队各角色（调度官、项目负责人、码农、审核官、调试工程师）之间的任务派发和结果回收提供统一的格式标准，确保通信可解析、可追溯、可降级。

---

## 一、任务单格式

每个任务单由两部分组成：**JSON 信封**（一行，放最前面）+ **Markdown 主体**。

### 1.1 JSON 信封

6 字段极简格式，一行，紧贴在 `## 任务单` 标题之前或紧随其后（建议放在标题下一行）：

```json
{"task_id":"task-YYYYMMDD-NNN","from":"角色名","to":"角色名","clarification_rounds":0,"status":"pending","depends_on":[]}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `task_id` | string | 任务唯一标识，格式 `task-YYYYMMDD-NNN`（年月日-序号），如 `task-20260510-001` |
| `from` | string | 派发者角色名，如"调度官"、"项目负责人" |
| `to` | string | 执行者角色名，如"码农"、"审核官" |
| `clarification_rounds` | number | 已使用的澄清轮次，初始为 0，最大 2 |
| `status` | string | 任务状态：`pending` / `in-progress` / `done` / `blocked` |
| `depends_on` | string[] | 依赖的任务ID列表，如 ["task-20260510-001"]。调度官据此编排DAG执行顺序 |

### 1.2 Markdown 主体

```markdown
## 任务单 #task-YYYYMMDD-NNN

| 字段 | 值 |
|------|-----|
| 派发者 | [角色名] |
| 执行者 | [角色名] |
| 澄清轮次 | 0/2 |
| 状态 | pending |
| 依赖任务 | [task_id列表或"无"] |

### 技术上下文
- [环境信息：语言/框架/数据库等，按实际填写，无则省略该行]
- [相关文件路径列表]
- [现有代码模式或架构约束]

### 交付物
[精确描述要产出什么，1-3 句话]

### 约束与验收
- **必须**：[硬性要求列表]
- **禁止**：[红线列表]
- **验收**：[可验证的通过条件]

### 澄清记录
（初始为空，执行中按需追加行）
```

**澄清记录**追加格式（每轮一行）：

```markdown
| 轮次 | 问题 | 已尝试的调查 |
|------|------|-------------|
| 1/2 | [具体问题] | [已调查的文件/搜索] |
| 2/2 | [具体问题] | [已调查的文件/搜索] |
```

## 二、澄清请求块格式

子代理执行过程中发现信息不足时，在本次输出末尾追加澄清请求块。

### 2.1 格式

```markdown
### 澄清请求

| 轮次 | 问题 | 已尝试的调查 |
|------|------|-------------|
| N/2 | [具体问题，精确到字段名或文件名] | [已 Grep 的文件 / 已 Read 的路径 / 已尝试的搜索词] |
```

### 2.2 发起规则

1. **先查后问**：先通过 Read / Grep 在代码库中自行查找答案，确认代码库中没有答案后再发起澄清请求
2. **上限 2 轮**：`clarification_rounds` 达到 2 时不再发起新的澄清请求，改为在完成报告中标注"未确认假设"
3. **每轮一个问题**：一次澄清请求只问一个问题，避免堆砌多个疑问

### 2.3 填写要求

- **问题**：精确到具体字段名、函数名、文件路径或行为预期，避免开放式提问
- **已尝试的调查**：列出已搜索的关键词、已读取的文件路径、已排除的可能——让接收方知道哪些路径已经走过，不需重复

## 三、完成报告块格式

子代理完成任务后，在本次输出末尾追加完成报告块。

### 3.1 格式

```markdown
### 完成报告

| 字段 | 值 |
|------|-----|
| 任务 | [task_id] |
| 文件 | [路径:行号，改动行数；多文件用<br>分隔] |
| 说明 | [执行了什么操作，1-3 句话] |
| 自检 | [构建/测试/lint 结果；未执行则写"未执行"] |
| 风险 | [需审核官或调度官注意的问题；无则写"无"] |
| 未确认假设 | [执行中做出的未经确认的假设；无则写"无"] |
```

### 3.2 填写要求

- **文件**：精确到行号，如 `src/auth.ts:42-58，3 处改动`。多文件用 `<br>` 换行分隔
- **说明**：简述改了什么、为什么改，不赘述执行过程
- **自检**：如有构建命令则执行并写结果；如无则写"未执行"
- **风险**：边界情况、潜在回归、依赖变更等需注意的点
- **未确认假设**：澄清轮次用尽后仍不确定而做出的假设，列在此处供调度官终审时核查

## 四、向后兼容声明

### 4.1 接收端行为

子代理（码农、审核官、调试工程师、项目负责人）接收输入时：

1. **检测**：检查输入文本是否以 `## 任务单 #` 或包含 `{"task_id":"task-` 开头
2. **有任务单** → 解析 `task_id`、`from`、`to`、`status` 字段和 Markdown 主体，按任务单中指定的交付物和约束执行
3. **无任务单** → 降级为纯文本理解模式，照常理解自然语言指令并执行，不因缺少任务单而报错、拒绝或中断工作

### 4.2 设计原则

- 任务单是**增强**而非**强依赖**——有则结构化、可追溯，无则照常工作
- 不强制要求调度官每次派发必附任务单，支持渐进式采用
- 降级模式下，子代理仍按自身角色约束执行（如码农不改测试文件、审核官只看不改等）
